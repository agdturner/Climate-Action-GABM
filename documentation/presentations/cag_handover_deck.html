What is this, and what's the one model to hold?

100 LLM-driven citizens debate 6 UK climate policies over repeated "days". Two broadcasters — one pro-climate, one anti — push competing messages; citizens talk to neighbours, then re-take the survey each night. Everyone is seeded from real YouGov data. The whole codebase is one pipeline:

If you remember one thing: everything is the day loop. The other five boxes feed it or read from it.

What runs when I hit "go"?

Each citizen is first seeded from their real YouGov answer (Day 0). Then every day repeats the same rhythm — two broadcasts, peer chat, a memory pass, a re-survey — for N days.

The detail that trips people up: memory compresses before the survey — older days are summarised before the agent answers again.

The memory trick — what does the model see?

Before every survey question, each citizen's prompt is rebuilt as six sections: freshest days verbatim, older days compressed. Two independent "scopes" decide what goes in.

The invariant: context scope (what I've been thinking about) and question scope (what we're asking now) are set independently — that's what lets package mode stay broad and precise.

How do I see what actually happened?

Every run drops a timestamped folder of CSVs (on AIRE, under $SCRATCH). You don't need all of them — these four, in order, tell the whole story.

Who the agents are — demographics, values, vote history.

Act 3. What is AIRE?

AIRE is Leeds's HPC cluster, scheduled by Slurm. The golden rule: you don't run heavy work yourself — you submit a job, and Slurm runs it on a shared compute node when resources free up.

Three kinds of node

Login node
Where you SSH in. Edit files, build the environment, submit jobs. Never run simulations here.
Compute node
Where jobs actually run. 168 cores, ~773 GB. You get a slice via Slurm, not by SSH.
GPU node
Requested explicitly (partition=gpu). This is where our vLLM model server runs.

Two places for data

$HOME
65 GB · backed up.
Code, scripts, the conda env.
$SCRATCH
1 TB · not backed up.
All run output.
Two hard rules. Output goes to $SCRATCH, never $HOME or the repo tree (filling $HOME can suspend the account). And modules / conda don't carry over from the login node — every job re-loads them itself.

Our repo already satisfies the AIRE contract: a headless CLI, all parameters as flags, output via --outdir, logging to stdout.

One AIRE run, end to end

You submit one job. Inside it, the GPU node boots a model server and then runs the simulation against it — both on the same node, talking over localhost.

The trick: the model server and the simulation run side by side on one GPU node, so the LLM calls never leave the machine.

The launcher — aire/run.sh

One deliberately thin Slurm script. It owns the GPU + server plumbing; every research knob stays on the sbatch line. In order, the job does five things:

1
Start vLLM in an Apptainer container, serving $HF_MODEL (default Qwen/Qwen3-8B).
2
Wait until ready — poll /v1/models until it answers (up to 25 min on a cold model download).
3
Run the sim — load conda, then python -m cag --provider local --base-url … --outdir … "$@", forwarding all your flags.
4
Save to $SCRATCH — results land in $SCRATCH/cag/runs/run_<jobid>/, never the repo.
5
Shut the server down — a cleanup trap kills vLLM on exit, win or lose.
# a real submission — preset for the bulk, one flag for the experimental fork
sbatch aire/run.sh --preset r14_canonical --exposure-targets split50

One-time prep: an HF token, conda env create -f environment.yaml, and apptainer pull the vLLM image. After that, every experiment is just a new sbatch line.

The entry point — __main__.py

What python -m cag actually does. This is the file that makes the repo AIRE-ready: headless, every parameter a flag, output via --outdir, logs to stdout (which Slurm captures into the .out file).

On AIRE, run.sh fills in the model plumbing (--provider local --base-url … --outdir $SCRATCH/…) and forwards the rest of your flags straight to this entry point.
